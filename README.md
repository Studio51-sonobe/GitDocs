# Git入門ガイド

〜バージョン管理の基礎から理解する〜

---

## 1. Gitとは

Gitは、ソフトウェア開発において広く使用されている「バージョン管理システム」です。

Gitを使うことで、プロジェクトの変更履歴を記録し、複数人で効率的に協働開発を行うことができます。また、誤った変更を元に戻したり、過去の状態を参照したりすることも簡単に行えます。

特に、Gitは「分散型」のバージョン管理システムであり、各開発者が完全な履歴のコピーを持つことができるという特徴があります。これにより、ネットワークに接続していない状態でも作業を続けることができ、柔軟な開発スタイルを実現します。

---

## 2. バージョン管理とは

バージョン管理とは、ファイルやプロジェクトの変更履歴を管理する仕組みのことです。特にソフトウェア開発においては、コードの変更を追跡し、必要に応じて過去の状態に戻せるようにすることが重要です。

### バージョン管理が解決する課題

- **複数人での同時作業**: チームメンバーが同じファイルを編集する際の競合を管理できます
- **変更履歴の記録**: 誰が、いつ、何を変更したかを明確に記録できます
- **過去の状態への復元**: 問題が発生した場合、動作していた過去の状態に戻すことができます
- **実験的な変更の管理**: 本番環境に影響を与えずに新機能を試すことができます
- **バックアップ**: コードの喪失を防ぐ安全な保管場所として機能します

バージョン管理システムを使わない場合、「最終版.txt」「最終版2.txt」「本当の最終版.txt」といった名前のファイルが乱立してしまい、どれが最新かわからなくなることがあります。バージョン管理システムは、このような問題を体系的に解決します。

---

## 3. Gitでできること

Gitは多様な機能を提供していますが、ここでは主要な操作について概要を説明します。これらの操作を組み合わせることで、効率的な開発ワークフローを実現できます。

### 主要な操作

- **クローン（Clone）**: 既存のリポジトリを自分の環境にコピーします
- **プル（Pull）**: リモートリポジトリの最新の変更を取得し、自分の環境に統合します
- **ブランチ（Branch）**: 開発の枝分かれを作成し、独立した作業を行います
- **コミット（Commit）**: 変更内容を記録し、履歴として保存します
- **プッシュ（Push）**: ローカルの変更をリモートリポジトリに送信します
- **マージ（Merge）**: 異なるブランチの変更を統合します
- **フェッチ（Fetch）**: リモートリポジトリの情報を取得しますが、統合は行いません

これらの操作は、チームでの協働開発において日常的に使用されます。それぞれの操作には明確な役割があり、適切に使い分けることで、スムーズな開発を実現できます。

## 4. 用語の詳細説明

ここでは、前のセクションで登場した主要な用語について、より詳しく解説します。

### リポジトリ（Repository）

リポジトリとは、プロジェクトのファイルと変更履歴を保管する場所です。「倉庫」という意味を持ち、Gitではすべてのバージョン情報がここに保存されます。

- **ローカルリポジトリ**: 自分のコンピュータ上にあるリポジトリです。ここで作業を行い、変更を記録します。
- **リモートリポジトリ**: サーバー上にあるリポジトリで、チームメンバーと共有します。GitHub、GitLab、Bitbucketなどのサービスを利用することが一般的です。

### クローン（Clone）

クローンは、リモートリポジトリの完全なコピーを自分のコンピュータに作成する操作です。プロジェクトに参加する最初のステップとして行われることが多く、この操作によってすべての履歴を含む完全なリポジトリが手元に作られます。

例えば、GitHubで公開されているオープンソースプロジェクトをクローンすることで、そのプロジェクトの全ファイルと変更履歴を入手し、自分で開発を始めることができます。

### プル（Pull）

プルは、リモートリポジトリから最新の変更を取得し、自分のローカルリポジトリに統合する操作です。プッシュとは逆の動作で、他のメンバーが行った変更を自分の環境に反映させます。

定期的にプルを行うことで、自分の作業が最新の状態に基づいていることを確認でき、後から発生する競合を減らすことができます。

### ブランチ（Branch）

ブランチは、開発の「枝分かれ」を表します。メインの開発ラインから分岐して、独立した作業を行うための仕組みです。

例えば、安定版のコードを保持する「mainブランチ」から「feature/new-login」という新しいブランチを作成し、ログイン機能の開発を進めます。この間、mainブランチは影響を受けず、安定した状態を保ちます。開発が完了したら、マージによって変更を統合します。

### コミット（Commit）

コミットは、変更内容を記録する操作です。ファイルを編集した後、その変更を履歴として保存することで、後から「いつ、何を変更したか」を振り返ることができます。

各コミットには、変更内容を説明する「コミットメッセージ」を付けます。このメッセージは、他の開発者（または未来の自分）が変更の意図を理解するために非常に重要です。

コミットは「スナップショット」のようなもので、プロジェクトの特定時点の状態を保存します。問題が発生した場合、過去の正常なコミットに戻ることができます。

### プッシュ（Push）

プッシュは、ローカルリポジトリで行ったコミット（変更記録）をリモートリポジトリに送信する操作です。この操作により、自分の変更をチームメンバーと共有できます。

例えば、新しい機能を開発してローカルでコミットした後、プッシュを行うことで、その機能をチーム全体で利用できるようになります。

### マージ（Merge）

マージは、異なるブランチ（開発の分岐）の変更を統合する操作です。例えば、新機能を開発するために作成した別ブランチの内容を、メインのブランチに取り込む際に使用します。

複数の開発者が同じファイルを編集していた場合、マージ時に「競合（コンフリクト）」が発生することがあります。この場合、どちらの変更を採用するか、または両方を組み合わせるかを手動で決定する必要があります。

### フェッチ（Fetch）

フェッチは、リモートリポジトリの最新情報を取得する操作ですが、プルとは異なり、自動的には統合（マージ）を行いません。まず情報だけを取得して、どのような変更があったかを確認してから、手動でマージするかどうかを決めたい場合に使用します。

フェッチは、より慎重に変更を取り込みたい場合や、リモートの状態を確認したいだけの場合に便利です。

### Git-LFS（Git Large File Storage）

Git-LFSは、Gitで大きなファイルを効率的に扱うための拡張機能です。Gitは本来、テキストファイルやソースコードのようなサイズの小さいファイルを扱うことを想定して設計されていますが、画像、動画、3Dモデル、大きなデータセットなどの大容量ファイルを通常の方法で管理すると、リポジトリのサイズが急速に肥大化してしまいます。

Git-LFSを使用すると、大きなファイルの実体は別のストレージに保存され、リポジトリには「ポインタファイル」と呼ばれる小さなテキストファイルだけが保存されます。これにより、リポジトリのサイズを小さく保ちながら、大きなファイルをバージョン管理できます。

#### Git-LFSが適している場面

- **画像ファイル**: デザイン素材、スクリーンショット、アイコンなど
- **動画ファイル**: チュートリアル動画、デモ映像など
- **音声ファイル**: 音楽、効果音など
- **3Dモデル**: ゲーム開発やCGで使用するモデルファイル
- **大きなデータセット**: 機械学習の学習データなど
- **コンパイル済みバイナリ**: 実行可能ファイルやライブラリ

#### Git-LFSの仕組み

通常のGitでは、ファイルを変更するたびにその全体がリポジトリに保存されます。一方、Git-LFSでは以下のように動作します：

1. 大きなファイルをコミットすると、その実体はLFSストレージ（通常はリモートサーバー）に送信されます
2. リポジトリには、ファイルへの参照情報を含む小さなポインタファイルが保存されます
3. クローンやプルを行う際、必要なファイルだけがLFSストレージからダウンロードされます

これにより、クローン時間が短縮され、ディスク使用量も削減されます。

## 5. 開発フローの説明

ここでは、Gitを使った典型的な開発フローを説明します。このフローは、個人開発でもチーム開発でも基本となる流れです。

### 基本的な開発フロー

#### 1. プロジェクトへの参加

まず、リモートリポジトリをクローンして、プロジェクトの完全なコピーを自分のコンピュータに作成します。これにより、ローカル環境で作業を開始できます。

#### 2. 最新状態の取得

作業を始める前に、プルを実行して他のメンバーの最新の変更を取得します。これにより、古いコードベースで作業してしまうことを防ぎます。

#### 3. ブランチの作成

新しい機能や修正を行う際は、専用のブランチを作成します。これにより、メインのコードベースに影響を与えずに安全に作業できます。

#### 4. コードの編集とコミット

ファイルを編集したら、意味のある単位でコミットを作成します。一つの機能や修正を完成させるまでに、複数のコミットを行うことが一般的です。各コミットには、変更内容を明確に説明するメッセージを付けます。

#### 5. リモートへのプッシュ

ローカルでの変更がある程度まとまったら、プッシュを行ってリモートリポジトリに反映させます。これにより、他のメンバーがあなたの作業を確認できるようになります。

#### 6. レビューとマージ

多くのプロジェクトでは、変更をメインブランチに統合する前に、他のメンバーによるコードレビューが行われます。レビューで承認されたら、ブランチをメインブランチにマージします。

### 継続的な開発サイクル

上記のフローは繰り返し実行されます。定期的にプルを行って最新の状態を保ち、新しいブランチを作成して機能開発や修正を行い、コミットとプッシュを通じてチームと変更を共有します。

このサイクルを通じて、プロジェクトは着実に進化し、複数の開発者が効率的に協働できるようになります。

## 6. 具体的な操作手順

ここでは、Windowsにおける環境構築と、主要なGitクライアントツールを使った具体的な操作方法について説明します。

### Windowsにおけるgitのセットアップ

Windowsで Git を使用するには、Git for Windows をインストールする必要があります。

#### インストール手順

1. **Git for Windowsのダウンロード**
   - 公式サイト（https://git-scm.com/download/win）から最新版のインストーラーをダウンロードします

2. **インストーラーの実行**
   - ダウンロードしたインストーラーを実行します
   - 基本的にはデフォルト設定のまま「Next」を押して進めて問題ありません

3. **重要な設定項目**
   - **エディタの選択**: コミットメッセージを入力するエディタを選択します（Visual Studio Code、Vim、Notepad++など）
   - **PATH環境変数**: 「Git from the command line and also from 3rd-party software」を選択することで、コマンドプロンプトやPowerShellからもGitを使用できます
   - **改行コードの扱い**: 「Checkout Windows-style, commit Unix-style line endings」が推奨されます

4. **インストールの完了**
   - インストールが完了したら、コマンドプロンプトまたはPowerShellを開き、以下のコマンドでインストールを確認します
   ```
   git --version
   ```

5. **初期設定**
   - ユーザー名とメールアドレスを設定します（コミット履歴に記録されます）
   ```
   git config --global user.name "あなたの名前"
   git config --global user.email "your.email@example.com"
   ```

### Git-LFSのセットアップ

Git-LFSを使用するには、別途インストールと設定が必要です。

#### インストール手順

1. **Git-LFSのダウンロード**
   - 公式サイト（https://git-lfs.github.com/）から最新版のインストーラーをダウンロードします
   - Git for Windowsに含まれている場合もあります

2. **インストーラーの実行**
   - ダウンロードしたインストーラーを実行します

3. **Git-LFSの初期化**
   - コマンドプロンプトまたはPowerShellで以下のコマンドを実行します
   ```
   git lfs install
   ```
   - このコマンドは1回だけ実行すれば、その後のすべてのリポジトリで有効になります

4. **追跡するファイルの指定**
   - リポジトリで管理したい大きなファイルの種類を指定します
   ```
   git lfs track "*.psd"
   git lfs track "*.mp4"
   git lfs track "*.zip"
   ```
   - この設定は`.gitattributes`ファイルに保存されます

5. **確認**
   - 追跡されているファイルを確認します
   ```
   git lfs track
   ```

### Forkを使った操作

Forkは、直感的で視覚的に優れたGitクライアントです。Windows、macOS、Linuxで利用できます。

#### 初期設定

1. **Forkのダウンロードとインストール**
   - 公式サイト（https://git-fork.com/）からダウンロードし、インストールします

2. **リポジトリを開く**
   - 「File」→「Open Repository」から既存のローカルリポジトリを開く、または
   - 「File」→「Clone」でリモートリポジトリをクローンします

#### 主要な操作

**クローン**
1. 「File」→「Clone」を選択
2. リポジトリのURLを入力
3. 保存先のフォルダを選択
4. 「Clone」ボタンをクリック

**ブランチの作成**
1. 左サイドバーの「Branches」を右クリック
2. 「New Branch」を選択
3. ブランチ名を入力し、作成元となるブランチを選択
4. 「Create Branch」をクリック

**変更のコミット**
1. ファイルを編集すると、左下の「Changes」タブに変更されたファイルが表示されます
2. コミットに含めたいファイルにチェックを入れます
3. 下部のテキストボックスにコミットメッセージを入力
4. 「Commit」ボタンをクリック

**プッシュ**
1. 上部ツールバーの「Push」ボタンをクリック
2. プッシュ先のリモートとブランチを確認
3. 「Push」をクリック

**プル**
1. 上部ツールバーの「Pull」ボタンをクリック
2. プル元のリモートとブランチを確認
3. 「Pull」をクリック

**マージ**
1. マージ先のブランチにチェックアウト（ブランチをダブルクリック）
2. マージしたいブランチを右クリック
3. 「Merge into current branch」を選択
4. 競合がある場合は、競合解決画面が表示されます

### SourceTreeを使った操作

SourceTreeは、Atlassian社が提供する無料のGitクライアントです。Windows、macOSで利用できます。

#### 初期設定

1. **SourceTreeのダウンロードとインストール**
   - 公式サイト（https://www.sourcetreeapp.com/）からダウンロードし、インストールします
   - Atlassianアカウントでのログインが必要です

2. **Gitの設定**
   - 初回起動時に、Git for Windowsのパスを設定します
   - ユーザー名とメールアドレスを設定します

#### 主要な操作

**クローン**
1. 「Clone」ボタンをクリック
2. 「Source Path / URL」にリポジトリのURLを入力
3. 「Destination Path」に保存先を指定
4. 「クローン」をクリック

**ブランチの作成**
1. 上部の「ブランチ」ボタンをクリック
2. 新しいブランチ名を入力
3. 「ブランチを作成」をクリック

**変更のコミット**
1. ファイルを編集すると、「ファイルステータス」タブに変更が表示されます
2. コミットしたいファイルを選択し、「ステージへインデックス」をクリック
3. 下部のコミットメッセージ欄にメッセージを入力
4. 「コミット」ボタンをクリック

**プッシュ**
1. 上部の「プッシュ」ボタンをクリック
2. プッシュしたいブランチを選択
3. 「プッシュ」をクリック

**プル**
1. 上部の「プル」ボタンをクリック
2. プル元のリモートブランチを確認
3. 「OK」をクリック

**マージ**
1. マージ先のブランチにチェックアウト
2. 左サイドバーのブランチ一覧から、マージしたいブランチを右クリック
3. 「現在のブランチへマージ」を選択
4. 競合がある場合は、競合解決ツールが起動します

### TortoiseGitを使った操作

TortoiseGitは、Windowsエクスプローラーに統合されるGitクライアントです。右クリックメニューから操作できるため、直感的に使用できます。

#### 初期設定

1. **TortoiseGitのダウンロードとインストール**
   - 公式サイト（https://tortoisegit.org/）からダウンロードし、インストールします
   - Git for Windowsが事前にインストールされている必要があります
   - 日本語ランゲージパックも別途ダウンロード可能です

2. **初期設定**
   - デスクトップやフォルダを右クリック→「TortoiseGit」→「Settings」を選択
   - 「Git」→「Config」で、ユーザー名とメールアドレスを設定します

#### 主要な操作

**クローン**
1. エクスプローラーで保存先のフォルダを開く
2. 右クリック→「Git Clone...」を選択
3. 「URL」にリポジトリのURLを入力
4. 「Directory」で保存先を確認
5. 「OK」をクリック

**ブランチの作成**
1. リポジトリフォルダ内で右クリック→「TortoiseGit」→「Create Branch...」を選択
2. 「Branch」にブランチ名を入力
3. 必要に応じて「Switch to new branch」にチェック
4. 「OK」をクリック

**変更のコミット**
1. リポジトリフォルダ内で右クリック→「Git Commit -> "main"...」を選択
2. コミットに含めたいファイルにチェック
3. 上部のメッセージ欄にコミットメッセージを入力
4. 「Commit」ボタンをクリック

**プッシュ**
1. リポジトリフォルダ内で右クリック→「TortoiseGit」→「Push...」を選択
2. プッシュ先のリモートとブランチを確認
3. 「OK」をクリック

**プル**
1. リポジトリフォルダ内で右クリック→「TortoiseGit」→「Pull...」を選択
2. プル元のリモートとブランチを確認
3. 「OK」をクリック

**マージ**
1. マージ先のブランチにチェックアウト
2. リポジトリフォルダ内で右クリック→「TortoiseGit」→「Merge...」を選択
3. マージしたいブランチを選択
4. 「OK」をクリック
5. 競合がある場合は、競合解決ツール（TortoiseGitMerge）が起動します

**競合の解決**
1. 競合が発生すると、該当ファイルが赤いアイコンで表示されます
2. 競合ファイルを右クリック→「TortoiseGit」→「Edit conflicts」を選択
3. TortoiseGitMergeで、左側（自分の変更）、右側（相手の変更）を確認しながら、下部の結果ペインを編集
4. 保存してマージツールを閉じると、競合が解決済みとしてマークされます
5. すべての競合を解決したら、コミットを実行します

## 7. Git-flowについて

Git-flowは、Gitを使った開発において広く採用されているブランチ運用モデルの一つです。チーム開発でブランチをどのように使い分けるかを体系化したもので、開発プロセスを整理し、リリース管理を効率化するために役立ちます。

### Git-flowの主要なブランチ

Git-flowでは、以下のような役割を持つブランチを使い分けます。

#### メインブランチ

- **main（またはmaster）ブランチ**: 本番環境にリリースされる、常に安定した状態のコードを保持します。このブランチには、リリース可能な状態のコードのみが統合されます。

- **developブランチ**: 開発の中心となるブランチです。次のリリースに向けて、完成した機能がここに統合されていきます。mainブランチよりは不安定ですが、基本的には動作する状態を保ちます。

#### サポートブランチ

- **featureブランチ**: 新機能を開発するためのブランチです。developブランチから分岐し、開発が完了したらdevelopブランチにマージされます。命名規則は「feature/機能名」が一般的です。

- **releaseブランチ**: リリース準備のためのブランチです。developブランチから分岐し、リリースに必要な最終調整（バージョン番号の更新、軽微なバグ修正など）を行います。準備が完了したら、mainとdevelopの両方にマージされます。

- **hotfixブランチ**: 本番環境で発見された緊急のバグを修正するためのブランチです。mainブランチから分岐し、修正後はmainとdevelopの両方にマージされます。

### Git-flowの利点

- **役割の明確化**: 各ブランチの役割が明確なため、チームメンバー全員が同じ認識を持って作業できます
- **安定性の確保**: mainブランチは常にリリース可能な状態を保つため、いつでも本番環境にデプロイできます
- **並行開発の支援**: 複数の機能を同時に開発しながら、互いに影響を与えずに作業できます
- **リリース管理**: リリースプロセスが体系化され、計画的なリリースが可能になります

### Git-flowの基本的な流れ

1. 新機能を開発する際は、developブランチからfeatureブランチを作成
2. featureブランチで開発を行い、完了したらdevelopにマージ
3. リリースの準備ができたら、developからreleaseブランチを作成
4. releaseブランチで最終調整を行い、完了したらmainとdevelopにマージ
5. 本番環境で緊急のバグが見つかった場合は、mainからhotfixブランチを作成し、修正後にmainとdevelopにマージ

### 注意点

Git-flowは強力なモデルですが、すべてのプロジェクトに適しているわけではありません。小規模なプロジェクトや、継続的デプロイメントを行うプロジェクトでは、よりシンプルな運用モデル（GitHub FlowやGitLab Flowなど）が適している場合もあります。

プロジェクトの規模、チームの体制、リリースサイクルなどを考慮して、最適なブランチ戦略を選択することが重要です。

## 8. まとめ

Gitは、現代のソフトウェア開発において不可欠なツールです。バージョン管理の概念を理解し、基本的な操作（クローン、コミット、プッシュ、プル、フェッチ、マージ）を習得することで、効率的な開発が可能になります。

最初は用語や概念が複雑に感じられるかもしれませんが、実際に使っていくうちに自然と理解が深まります。まずは基本的なフローを試してみて、徐々に高度な機能を学んでいくことをお勧めします。

Gitを使いこなすことで、より安全で協調的な開発環境を構築し、プロジェクトの品質を高めることができるでしょう。
